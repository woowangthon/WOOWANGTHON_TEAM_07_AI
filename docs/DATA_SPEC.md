# 데이터 명세서 (Data Spec)

> AI 파트가 쓰는(또는 쓸 예정인) 외부 데이터셋의 내용, 품질 문제, 연결 방법, AI 도구 스키마와의 대응을 정리한다.
> 데이터셋 목록의 원본은 [`data/sources.json`](../data/sources.json)이고, 이 문서는 그 해설이다.
>
> 최종 갱신: 2026-11-13
> - 원본을 받아 분석한 4종(§4.1~4.4)과 BE가 수집하기로 한 4종(§4.7)을 다룬다.
> - 공식 페이지 정보(명칭·갱신 주기·제공 형태)는 2026-11-13에 서울 열린데이터광장에서 확인했다.
> - OA-22740, OA-22725는 사이트 오류로 페이지를 열지 못해 확인하지 못했다.
> - OA-15994는 BE가 Open API로 실제 호출한 결과(BE 이슈 #9, PR #48, `BE/docs/api-notes.md`)를 §4.2에 반영했다. 숫자는 BE 샘플 JSON과 `data/raw/`의 CSV를 AI가 다시 비교해 확인했다.
> - 행 수와 값 분포 같은 통계는 원본을 `data/raw/`에 넣은 뒤 `python scripts/check_raw_data.py`로 확인한다.

핵심 정리:

- **"실시간"이 아니라 "1시간 단위"다.** 운행 상태의 원천인 OA-15994의 갱신 주기는 "매시"다(공식 설명). 응답에는 갱신 시각이 없어 실제 주기는 확인할 수 없다. 안내 문구는 "○분 전 기준"(BE 수집 시각 기준)으로 정직하게 표시하고, 서비스 소개에서 "실시간" 표현을 조정한다.
- **상태는 실제로 자주 바뀐다.** 하루 차이 CSV와 API를 비교하면 2,809건 중 100건의 사용 여부가 바뀌었다 (§4.2).
- **경로·시간 계산 데이터의 공백이 대부분 메워진다.** 경로는 OA-22724, 시간표는 OA-101로 해결된다. 남는 공백은 §7에 있다.
- **이 두 API는 DB에 미리 다 담을 수 없는 "조회형"이다.** 저장 구조를 조회형에 맞게 나눠야 한다 (§2).
- 커버리지는 "1~8호선"이 아니라 **서울교통공사 운영 역**이다 (§5).

## 2. 데이터 흐름과 저장 원칙

데이터셋은 받는 방식에 따라 두 종류로 나뉜다. `sources.json`의 `access` 필드에 적는다.

| 종류 | 데이터셋 | 처리 방식 |
|---|---|---|
| **목록형** (`bulk`) | OA-22725, OA-15994, OA-21212, OA-22740 | 전체 목록을 주기적으로 받아 전처리 후 DB에 저장 |
| **조회형** (`query`) | OA-22724, OA-101, OA-22749 | 역·경로마다 요청. 아래처럼 나눠 처리 |

조회형은 다시 두 가지로 나눠 처리한다.

- **역 단위 조회 (OA-101 시간표, OA-22749 빠른하차)**: 역 수가 정해져 있으므로 BE가 하루 1회(또는 자료 변경 시) 모든 역을 미리 조회해 DB에 저장한다. 결과적으로 목록형과 같이 다룬다.
- **역 쌍 조회 (OA-22724 최단경로)**: 역 쌍과 시각 조합이 너무 많아 미리 저장할 수 없다. BE가 요청 시점에 API를 대신 호출하고 결과를 캐시한다.
  - 캐시 키 예: 출발역, 도착역, 시간대, 제외 환승역 목록.
  - API가 느리거나 실패하면 마지막 캐시 또는 "경로 계산 불가"로 응답한다. AI가 추측한 경로로 대신하지 않는다.

```text
[목록형 API] ─ 주기 수집 → [BE 전처리] → [DB] ─────────────┐
[역 단위 조회 API] ─ 하루 1회 전 역 조회 → [DB] ────────────┼→ [BE 데이터 계약] → [AI 도구 (src/tools)]
[역 쌍 조회 API] ←─ 요청 시 대신 호출 + 캐시 ─ [BE 프록시] ─┘   (읽기 전용 DB 뷰 또는 BE API)
```

원칙:

1. **고정 정보와 운행 상태를 나눈다.**
   - 고정 정보(역, 엘리베이터 목록, 층, 위치, 좌표, 시간표, 빠른하차)는 하루 1회 정도 갱신한다.
   - 운행 상태(`oprtngSitu`, `USE_YN`)는 원본 갱신 주기(매시)에 맞춰 수집하고, **수집 시각(`fetched_at`)을 함께 저장**한다. 수집에 실패하면 마지막 값을 유지하고 "오래된 정보"로 표시한다.
2. **AI는 DB 테이블이나 외부 API를 직접 부르지 않는다.** BE가 정한 계약(읽기 전용 DB 뷰 또는 BE API)만 쓴다. AI 코드에서는 `src/data/`에 데이터 소스 인터페이스를 두고, Mock 구현과 실데이터 구현을 바꿔 끼운다. 도구의 출력 모델(`src/models.py`)은 유지한다.
3. **외부 API 키는 BE만 가진다.** AI 레포의 `.env`에는 LLM 게이트웨이 키만 둔다.
4. **기준 시각은 수집 시각이다.** 원본에는 행별 상태 갱신 시각이 없다(`crtrYmd`는 등록일). `ElevatorStatusOutput.updated_at`에는 BE의 `fetched_at`을 넣는다.

## 3. 저장 구조 (`AI/data/`)

```text
data/
├── sources.json                      # 데이터셋 목록 (id, 공식 명칭, URL, 상태, 받는 방식, 갱신 주기, 파일, 컬럼)
├── raw/                              # 원본 그대로. 절대 수정하지 않는다 (커밋함)
│   └── <제공처>/<받은 날짜>/<원본 파일명>
│       예) seoul_opendata/2026-11-13/OA-22725_getFcElvtr.csv
└── processed/                        # 전처리 결과. 스크립트로만 만들고 커밋하지 않는다
```

규칙:

- **원본(`raw/`)은 받은 그대로 둔다.** 인코딩(CP949 등)도 바꾸지 않는다. 고칠 것이 있으면 전처리에서 고친다.
- **같은 데이터셋을 다시 받으면 새 날짜 폴더에 넣고** `sources.json`의 `file`, `received`를 바꾼다. 이전 스냅샷은 비교를 위해 남겨 둔다.
- 조회형 API는 **분석·테스트용 샘플 응답**만 보관한다. 예: 대표 역 몇 개의 시간표, 대표 경로 몇 개의 응답 JSON. 파일명에 조회 조건을 적는다. 예) `OA-22724_sindorim-gangnam_0900.json`.
- 제공처 폴더 이름: `seoul_opendata`(서울 열린데이터광장), `data_go_kr`(공공데이터포털), `seoul_metro`(서울교통공사 직접 제공) 등.
- 파일 하나가 10MB를 넘으면 커밋하지 않는다. `sources.json`에 받는 방법을 적고 `.gitignore`에 추가한다.
- `processed/`의 결과물과 테스트용 고정 데이터(`tests/` 아래)는 반드시 스크립트로 `raw/`에서 만든다. 손으로 만든 값을 섞지 않는다.

### 새 데이터셋을 추가하는 순서

1. `data/sources.json`에 항목을 추가한다. 원본이 아직 없으면 `status: "planned"`, `file: null`로 둔다.
2. 원본을 받으면 `data/raw/<제공처>/<받은 날짜>/`에 넣고 `status: "received"`, `file`, `received`, `columns`(원본 헤더 그대로)를 채운다.
3. `python scripts/check_raw_data.py`로 인코딩·헤더·행 수를 확인한다.
4. 이 문서의 §1 표와 §4에 데이터셋 절을 추가한다. 의미가 확실하지 않은 컬럼은 "추정"이라고 적는다.

### 4.2 OA-15994 서울교통공사_교통약자_이용시설_승강기_가동현황 ✅

공식 설명: 서울교통공사 각 역 승강기(엘리베이터, 에스컬레이터 등)의 가동 현황. **갱신 주기: 매시.** 제공 형태: Sheet, Open API. 공식 페이지에 컬럼 설명은 없다.

| 컬럼 | 의미 | 예시 | 비고 |
|---|---|---|---|
| `STN_CD` | 역 코드 (노선별) | `0222` | |
| `STN_NM` | 역명(노선) | `강남(2)`, `서울역(1)`, `삼각지(전쟁기념관)(4)` | 노선·부제 제거 필요 |
| `ELVTR_NM` | 승강기명 | `승강기)엘리베이터-강남 1번 출구측 외부#1` | OA-22725 `fcltNm`과 연결 |
| `OPR_SEC` | 운행 구간 | `B1-1F`, `B3-B2-B1` | 비정형 (§4.5) |
| `INSTL_PSTN` | 설치 위치 | `1번 출입구`, `교대 방면3-4` | |
| `USE_YN` | 사용 여부 | `사용가능`, `보수중` | 이름과 달리 Y/N이 아님. 고장과 정기 점검을 구분하지 않음 |
| `ELVTR_SE` | 승강기 구분 | `EV`, `ES`, `WL`, `MW` | 엘리베이터 / 에스컬레이터 / 휠체어리프트 / 무빙워크 |

- 휠체어 경로에는 `EV`만 쓴다. `ES`, `MW`는 제외한다.
- `WL`(휠체어리프트)은 안전 문제와 직원 호출 필요 때문에 포함 여부를 팀이 정한다 (§8).
- 갱신 주기가 확인된 유일한 상태 데이터이므로 **운행 상태의 기준 출처로 쓴다.** OA-22725의 `oprtngSitu`는 교차 검증용으로 쓴다.

#### API 응답 확인 (BE 이슈 #9, PR #48)

BE가 2026-11-13에 Open API(`SeoulMetroFaciInfo`)로 전체를 받아 확인했다. 샘플은 `BE/docs/samples/OA-15994_SeoulMetroFaciInfo_2026-11-13.json`(키 제거).

- 응답 구조: `SeoulMetroFaciInfo` → `list_total_count`, `RESULT`(`CODE`, `MESSAGE`), `row`. 정상 코드 `INFO-000`. 한 번에 최대 1,000건이라 3번 나눠 받는다.
- 필드는 CSV와 같은 7개, 모두 문자열이다.
- **갱신 시각 필드가 없다.** HTTP `Date` 헤더는 서버 응답 시각일 뿐이다. 따라서 원본 측정 시각(`observed_at`)은 비워 두고, 신선도는 BE 수집 시각(`fetched_at`)으로만 판단한다.
- **설비 고유 ID가 없다.** (`STN_CD`, `ELVTR_NM`) 조합이 2,809건에서 중복 없이 유일하므로 BE는 이 조합을 키로 쓴다.
- 노선 컬럼이 없다. 역명 괄호 번호(`서울역(1)`)로만 노선을 알 수 있고, 엘리베이터 866대 중 550대는 괄호가 없어 노선을 판정할 수 없다. 노선 매핑은 역·노선 원본(OA-22725 등)으로 해야 한다.
- `USE_YN`은 `사용가능`, `보수중` 두 값만 나왔다. BE DB는 `보수중 → 가동 안됨`, `사용가능 → 가동중`으로 저장한다.

CSV(이 레포 `data/raw/`, BE 확인 기준 11-12 작성 파일)와 API(11-13 호출)를 AI가 다시 비교한 결과:

| 항목 | CSV | API |
|---|---|---|
| 전체 행 / 엘리베이터(EV) | 2,809 / 866 (273역) | 2,809 / 866 (273역) |
| 전체 보수중 | 59 | 129 |
| 엘리베이터 보수중 | 8 | 21 |
| 키 차이 | — | 없음 (같은 2,809개) |
| `USE_YN`이 바뀐 행 | — | 100건 (사용가능→보수중 85, 보수중→사용가능 15). 엘리베이터만 15건 (14, 1) |

- 고정 정보(목록)는 같고 상태만 바뀐다. 상태는 반드시 수집 시각과 함께 다뤄야 한다.
- 예: Mock 데이터는 시청역 대체역으로 "을지로입구역 1번 출구 엘리베이터"를 안내하지만, API 호출 시점에는 이 엘리베이터가 `보수중`이었다. 대체역을 추천할 때도 그 시점의 상태를 다시 확인해야 한다 (현재 `find_alternative`가 대체역 상태를 확인하는 이유).

### 4.6 운행 상태 값의 의미 (교차 검증)

받은 시점 기준으로 `oprtngSitu=S`인 엘리베이터 8대와 `USE_YN=보수중`인 엘리베이터(`EV`) 8대가 정확히 일치했다.

| 역 | 엘리베이터 |
|---|---|
| 종각 | 상행 6-4 내부#1 |
| 신림 | 1번 출구측 외부#1 |
| 수서 | 1번 출구측 외부#1 |
| 마곡 | 내부1 (송정 방면 4-4) |
| 오목교 | 내부1 (목동 방면 7-1) |
| 석계(6) | 내부2 (태릉입구 방면 6-2) |
| 마들 | 외부2 (5번 출입구) |
| 태릉입구(7) | 외부2 (2번 출입구) |

따라서 `M = 정상`, `S = 중지(보수중)`로 판단한다. 공식 명세로 최종 확인한다.
이 일치는 **같은 시점에 받은 두 파일** 기준이다. 하루 뒤 API에서는 보수중 엘리베이터가 21대로 늘었으므로(§4.2), 교차 검증은 같은 시각에 받은 데이터끼리만 한다. 엘리베이터가 아닌 승강기 중에는 삼성 코엑스 연결계단 휠체어리프트가 `보수중`이었다.

### 4.7 수집 예정 데이터셋 (원본 받기 전, 공식 페이지 기준)

공식 페이지에는 네 데이터셋 모두 **출력 컬럼 설명이 없다.** 컬럼은 BE가 실제 응답을 받은 뒤 §3 절차대로 채운다. 아래 "AI에서의 용도"는 페이지 설명을 근거로 한 계획이다.

#### OA-22724 서울시 교통공사 지하철역 최단경로이동정보 현황

- **공식 설명**: 출발역과 도착역을 넣으면 최소시간·최단거리·최소환승 세 종류의 경로를 계산한다. 구간별 정차역, 역간 소요시간과 거리, 환승 여부를 준다. 경유역 지정과 **환승 제외역 지정** 옵션이 있고, 출발·도착 일시로 시간표 기준을 정한다.
- **제공**: Open API, 갱신 주기 "실시간", 데이터 갱신일 2025-10-17.
- **AI에서의 용도**:
  - `plan_trip`의 경로 계산을 이 API로 바꾼다. 지금의 "2호선 순환선 + 역당 2분 고정값"을 대체한다.
  - **환승역 엘리베이터가 고장이면 그 역을 "환승 제외역"으로 넣어 다시 요청한다.** 설계 검토 §2.3의 "고장 노드를 그래프에서 제외"를 직접 구현할 수 있다.
- **확인할 것**:
  - 환승 소요시간이 일반 보행 기준이라 휠체어 이동 시간이 반영되지 않았을 것이다. 엘리베이터 이동 여유를 따로 더해야 한다.
  - 서울교통공사 구간 밖(코레일·9호선 등)이 포함된 경로를 어떻게 다루는지 확인한다.

#### OA-101 서울교통공사_역코드로 지하철 열차 시간표 검색

- **공식 설명**: 역코드로 역별 열차 시간표를 검색한다. 시간표 기준이라 실제 도착시간과 다를 수 있다. 대상 노선이 설명에는 1~9호선, FAQ에는 1~8호선으로 적혀 있어 서로 다르다.
- **제공**: Open API, 갱신 주기 "비정기(자료변경시)", 데이터 갱신일 2026-11-12.
- **AI에서의 용도**:
  - 최악 대기 시간을 "배차 3분 + 여유 2분" 고정값 대신 실제 다음 열차 시각으로 계산한다.
  - 첫차·막차를 반영해 운행 시간 밖이면 `is_possible=False`로 응답한다 (설계 검토 §2.4).
- **확인할 것**: 요청 인자의 역코드가 `stnCd`(예: `0222`)와 같은 체계인지 확인한다. 다르면 대응표가 필요하다.

#### OA-22749 서울시 교통공사 지하철역 빠른하차정보 현황

- **공식 설명**: 역의 출구별로 계단·엘리베이터 등 시설과 가장 가까운 열차 칸과 문 번호, 그 시설의 위치를 준다. 호선·역코드·역명으로 조회한다.
- **제공**: REST API, 갱신 주기 "실시간", 데이터 갱신일 2025-10-17.
- **AI에서의 용도**: "엘리베이터와 가까운 **3-4번 칸**에 타세요" 같은 안내에 쓴다. 휠체어 이용자의 승강장 이동 거리를 줄이는, 이 서비스에서 가치가 큰 정보다.
- 도구 출력에 칸·문 번호 필드를 추가해야 한다. FE/BE 계약이 바뀐다 (§8).
- 참고로 OA-22725의 승강장 엘리베이터 위치(`교대 방면3-4`)에도 칸-문 번호가 들어 있다.

#### OA-22740 서울시 교통공사 지하철역 교통약자이용정보 엘리베이터 현황

- 공식 페이지가 2026-11-13에 접속 오류(서비스 지연 103)로 열리지 않아 내용을 확인하지 못했다.
- 이름으로 보아 엘리베이터 목록이며 OA-22725와 겹칠 수 있다. 원본을 받으면 `fcltNm`/`elvtrSn` 기준으로 비교한다.
- 두 데이터가 같으면 하나만 쓰고, 다르면 더 최신이고 층 정보가 구조화된 쪽을 기준으로 삼는다.

- 경로 API(OA-22724)가 범위 밖 구간을 지나는 경로를 돌려주면, 그 구간의 엘리베이터 상태는 "정보 없음"으로 안내한다.

| `ElevatorStatusOutput.freshness_minutes` | 현재 − `fetched_at` | 분. 매시 갱신이므로 최대 60분 + 수집 지연 |

**방향 판정이 가능해진다.** 상대식 승강장은 방향별로 엘리베이터가 따로 있다(예: 강남 "교대 방면3-4", "역삼 방면8-1"). 섬식 승강장은 한 대가 양방향을 담당한다(예: "섬식(외)"). 설계 검토 §2.3의 "이동 방향에 필요한 구간이 정상인지" 판정을 이 데이터로 구현할 수 있다. 층 정보로 "지상 → 대합실 → 승강장"이 이어지는지도 확인할 수 있다.

## 9. BE API 계약과 AI 도구의 대응 (2026-11-14)

기준: BE `docs/api-contract.md`(BE `main` 342a9d0). AI 쪽 리뷰는 BE 이슈 #14 코멘트(2026-11-14). 필드 단위 변환 규칙은 IMPLEMENTATION_STATUS §4.8에 있다.

| AI 도구 | BE API | 상태 |
|---|---|---|
| `resolve_station` | `GET /api/stations/{id}` (목록 API가 없어 ID 순으로 읽어 캐시) | ✅ 연동. 별칭·미지원 키워드는 AI 사전 |
| `get_elevator_status` | `GET /api/stations/{id}/elevators` | ✅ 연동. 판정 규칙은 BE §6.2와 같음 |
| `get_broken_elevators` | `GET /api/elevators/status` | ✅ 연동. 노선은 역 목록의 노선으로 거름 |
| `plan_trip` 대체역 | `GET /api/stations/{id}/alternatives` | ✅ 연동 (BE 계약 §8.1은 초안) |
| `plan_trip` 경로·소요 시간 | `GET /api/routes` (BE #37) | ❌ BE 미구현. AI Mock 2호선 계산을 추정으로 안내 |
| `plan_trip` 출발 시각 | `POST /api/departure-time` | ✅ 연동 (역산 모드만, AI 이슈 #6). 대기 시간 기본값 통일 전이라 AI가 여유 5분(배차 3 + 여유 2)·도보·진입·출구 값을 모두 명시해서 보낸다(BE 기본 `buffer_minutes` 0분을 쓰지 않음). 이동 시간은 #37 전까지 AI Mock 2호선 계산값. 순방향(출발 시각 기준)은 BE API가 없어 AI 계산 |
| (없음) | `GET /api/stations/{id}/arrivals` | 사용 안 함. 외부 출처 미연동으로 항상 `UNCONFIRMED` |

BE 데이터에서 확인한 사실 (데모 DB, 2026-11-14):

- 역 240개, 괄호를 뗀 기본 역명이 겹치는 역은 없다. AI Mock 역 46개(2호선 순환선 43개 포함)와 별칭 10개의 대상 역이 모두 BE에 있다.
- 역명에 괄호 부제가 55개 있다 (`잠실(송파구청)`, `신촌(지하)`, `총신대입구(이수)`). `서울역`만 "역"이 붙어 있다.
- 검색(`q`)은 부분 일치다 (`잠실` → 잠실, 잠실나루, 잠실새내). AI는 검색을 쓰지 않고 캐시한 목록에서 기본 역명으로 정확히 찾는다.
- 엘리베이터 상태는 2026-11-13 1회 수집 샘플이라 TTL(120분)을 넘어 대부분 `STALE`이다. 합성 설비 5건(`[DEMO/SYNTHETIC]`)만 확인 상태다(강남·선릉 `가동 안됨`, 역삼·교대·남부터미널 `가동중`).
