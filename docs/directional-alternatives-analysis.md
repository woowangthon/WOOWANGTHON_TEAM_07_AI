# 고장 대체역 안내와 이동 방면 분석

검토일: 2026-11-15. 아래 내용은 이 저장소의 코드와 BE API 계약을 감사한 결과이다. 실제 열차 탑승·현장 이동을 검증한 보고서가 아니다. 예시 역명은 대화 입력 형식 또는 기존 테스트 데이터의 값이며 현장 우회 추천으로 사용하면 안 된다.

## 판단

기존 대체역 추천은 이동 방면을 고려하지 않았다. 이미 열차에 탄 이용자의 현재 위치, 실제 탑승 노선, 다음 정차역, 목적지, 고장 역을 저장하는 슬롯도 없었다. 그 결과 후보가 현재 열차의 앞쪽인지, 이미 지나친 역인지, 반대편 승강장으로 이동할 수 있는지를 확인하지 않은 채 첫 후보를 권장했다.

이번 변경은 방향 정보가 부족할 때 구체적으로 묻고 여러 턴에 걸쳐 답을 수집한다. 정보가 모이면 **문의한 고장 역**의 실제 데이터 소스에서 후보를 조회하고, 확인된 상태와 확인되지 않은 이동 조건을 구분해서 설명한다. 앞·뒤 후보별 선택 조건을 설명하지만 특정 후보를 앞쪽/뒤쪽 또는 안전한 경로라고 판정하지 않는다. 방향까지 검증한 우회 경로 검색은 BE의 추가 계약이 필요하다.

## 기존 알고리즘과 확인 근거

| 계층 | 근거 코드·계약 | 실제 의미와 한계 |
|---|---|---|
| BE 후보 검색 | `BE/app/services/alternatives.py`의 `_load_adjacency`, `bfs_distances`, `get_alternatives`; `BE/docs/api-contract.md` §8.1 | `station_edges`의 ADJACENT 간선을 역 단위로 투영하여 양방향 BFS. TRANSFER는 역 그래프에서 제외. 기본 탐색 깊이 2는 설정값이며 후보까지 갈 수 있는 열차 방향이 아니다. |
| 후보 정렬 | 같은 코드, §8.1 | 대상 역과 노선 하나라도 공유 → 간선 수 → AVAILABLE 우선 → 신선도 → 역 ID. 이용자가 탑승한 노선·목적지·승강장 기준 정렬이 아니다. |
| 후보 상태 | `station_status`, `data_fresh`, `unknown_elevator_count` | AVAILABLE 또는 PARTIAL이면 후보 가능. PARTIAL은 필요한 동선에 쓰는 설비가 고장일 수도 있다. UNKNOWN/STALE은 정상의 근거가 아니다. |
| AI 수용 | `src/data/be_source.py::alternative_candidates`, `src/tools/trip.py::find_alternatives` | BE 후보의 ID·역명·간선 수·공유 노선·상태를 수용한다. BE `limitations`도 전달한다. 역간 거리(m)·보도 경사·횡단보도·승강장 방향은 제공되지 않는다. |
| Mock 경로 | `src/data/mock_source.py`, `src/data/mock_data.py` | 등록된 대체역 안내 우선, 없으면 인접역을 순회한다. 합성/개발 데이터이며 제품의 현장 근거로 사용하지 않는다. |
| 일반 경로 | `src/tools/trip.py::plan_trip`, BE `/api/routes` | 출발/도착 고장에는 후보를 붙이고 경유/환승 고장은 경고만 전달한다. 후보를 이용하도록 경로·시간을 재계산하지 않는다. 일반 경로의 `path`/`legs`는 현재 이용자가 탄 열차의 경로라는 증거가 아니다. |
| 시간표 방향 | BE 계약 §8.2, AI `SelectedTrain.direction_inferred` | BE는 경로 첫 두 역에 같은 열차가 정차하는 순서로 방향을 추정한다. 사용자의 현재 열차 식별·실제 승강장·반대편 환승 접근성을 검증한 값이 아니다. |
| 이전 버튼 | `response_builder._detour_actions`, 폴백 `_trip`, `_elevator` | `[고장 역, 후보 역]`를 임의 `path`로 만들어 지도 우회 경로 버튼을 냈다. 이번 변경에서 제거했다. |

역 좌표는 지리적 위치를 보여줄 수 있지만 이동 방향, 같은 승강장 연결, 역 밖의 계단 없는 동선을 증명하지 못한다. 노선 공유 역시 현재 탑승 노선 공유와 다르다. BFS 간선 수를 지상 이동 거리나 도보 분으로 바꾸지 않는다.

## 이번 구현

`src/tools/travel_context.py::directional_response`를 오케스트레이터와 독립 폴백 모두 먼저 실행한다. `타고 있…`, `승차 중`, `이동 중`, `열차 안`처럼 이동 상태를 언급하거나, `방면`/`반대 방향`/`진행 방향`과 대체·고장·하차·환승 문의가 함께 있으면 다음 정보를 수집한다. “역삼 방면 엘리베이터 상태” 같은 일반 상태 조회는 방면 단어만으로 가로채지 않는다.

| 내부 슬롯 | 명시적 입력 예 | 수집 이유 |
|---|---|---|
| `current` | 현재 강남역 / 지금 강남역 | 최근 정차역 또는 현재 위치. 최근 조회한 역을 위치로 간주하지 않는다. |
| `line` | 2호선 | 복수 노선 역에서 임의 노선 선택 방지. 현재 지원 번호 1~8만 수용한다. |
| `destination` | 목적지 잠실역 / 도착역 잠실역 | 고장 역이 목적지와 같은지 임의로 결정하지 않는다. |
| `broken` | 고장 역 사당역 | 실제 후보 검색 대상. 출발/경유/환승/도착 고장을 구별할 최소 근거. |
| `next` | 다음 정차역 역삼역 / 다음역 역삼역 | 내·외선/상·하행 같은 말의 의미를 임의로 매핑하지 않는다. 순환선·분기에서는 특히 필요하다. |
| `onboard` | 이미 타고 있어요 / 승차 중 / 열차 안 / 탑승 전 / 아직 안 탔어요 | 이미 탔는데 집→역 도보·진입·첫 대기를 다시 계산하는 오류 방지. |

역명은 기존 `resolve_station`으로 실제 지원 역을 확인한다. 모호하거나 미지원인 입력은 슬롯을 채우지 않고 다시 묻는다. 노선이 현재역/다음역의 알려진 소속 노선과 불일치하거나 두 역이 같으면 다음역을 지우고 재확인한다. **두 역이 같은 노선이라는 확인은 인접성 또는 그 열차의 정차 순서 확인을 뜻하지 않는다.**

수집 중인 정보는 `SessionContext.travel`에 저장하고 기존 세션 TTL(기본 30분)을 적용한다. 빈 슬롯 상태도 보존한다. 응답마다 최신 위치를 관측하는 기능은 없으므로 실제 이동을 추적하지 않는다. 완성된 분석 1회 후 슬롯을 지워, 다음 분석에서 오래된 위치/방면을 재사용하지 않는다. `취소`, `그만`, `새로`로 수집을 초기화할 수 있다. 명시적 새 질문, 일반 상태 조회, 전체 고장역 문의도 수집을 종료하고 기존 처리로 이어진다. `현재 강남, 목적지 잠실`처럼 역 접미사 없이도 라벨이 있으면 확인한다. 세션 원문을 새로 저장하지 않는다.

충분한 정보가 모이면 `plan_trip(broken, broken)`으로 후보를 조회한다. 집 출발 시각·열차 탑승 시각을 출력하지 않고, 사용자 제공 이동 정보, 고장 문의 역 후보, 앞/뒤 선택의 확인 조건을 설명한다. 이전의 단순 되묻기에서 끝나는 흐름과 달리, **후속 답변이 후보 조회와 조건 분석으로 이어진다.**

같은 고장 문의 역의 `get_elevator_status`도 조회해 실제 수집 시각을 `metadata.data_updated_at`에 전달하고, 상태·신선도 한계와 계획 도구 경고를 출력한다. 응답 생성 시각으로 대체하지 않는다. 세션 TTL과 설비 상태 TTL은 별개이며, BE 상태 신선도 판정을 수정하거나 후보 결과를 새로 캐시하지 않는다.

일반 상태 조회/일반 출발 계획에서 제공하는 후보에도 방향·승강장·반대 방면 환승·계단 없는 동선이 미검증임을 명시하고 필요한 이동 정보를 요청한다. 후보는 기존 순서를 보존하며 방향에 따른 순위인 것처럼 표현하지 않는다. PARTIAL은 “일부 엘리베이터 이용 불가”라고 표시한다. 후보 버튼은 `openStation {station_id}`로 상세 정보만 연다. 검증되지 않은 두 역 연결선을 액션에 넣지 않는다.

대체역이 포함된 도구 결과가 있으면 자유 생성 답변 대신 코드 템플릿을 출력한다. 기존 역명/시각 가드는 “반대편으로 갈아타세요” 같은 물리적 접근성 주장을 검증하지 못하므로, 역명이 맞더라도 근거 없는 이동 지시를 차단하기 위한 조치다. 모델과 `/api/chat` 입출력·LLM 도구 입력 스키마는 그대로다. 새 카드 종류는 텍스트 중심의 `need_travel_context`, `directional_alternatives`다.

## 시나리오별 판단 매트릭스

| 상황 | 이번 응답/처리 | 확정하면 안 되는 내용·추가 근거 |
|---|---|---|
| 탑승 전 출발역 고장 | 출발역을 고장 역으로 명시해 후보 조회, 현재/탈 노선·다음역·목적지 수집 | 후보로 가는 지상 접근 동선, 출입구 운영, 후보의 목적지 방향 승강장 접근성, 후보 사용 후 재계산 시간 |
| 승차 중 목적지 고장 | 최근 정차역·다음역과 목적지/고장역 분리 수집, 목적지 후보와 조건 설명 | 바로 다음역 하차 지시, 실제 열차 식별, 현재 위치와 후보 앞뒤, 후보에서 최종 목적지 지상 이동 |
| 현재역에서 내리기 어려움 | 고장 역을 현재역으로 명시하면 그 역 후보 조회 | 현재 승강장에서 계속 탑승 가능한지, 이미 하차했는지, 필요한 구간의 설비 상태 |
| 후보가 진행 방향 앞쪽 | 같은 승강장 하차 가능 등이 확인되면 계속 탑승을 검토할 수 있다고 조건부 설명 | 해당 후보가 실제 앞쪽이라는 판정, 열차가 그 역에 서는지, 출구 연결 |
| 후보가 뒤쪽/반대 방향 | 반대편 승강장까지 계단 없는 이동·재탑승 확인을 조건으로 설명 | 반대편 환승 가능 단정, 계단/육교 사용 지시, 추가 요금·환승시간 추정 |
| 도착역 일부 설비 고장 | PARTIAL의 필요한 구간이 막혔는지는 미확인으로 설명 | 고장 1대라는 이유만으로 역 전체 폐쇄 또는 전체 이용 가능 판단 |
| 환승역 고장 | 일반 계획은 환승역 경고, 방향 문의에서 고장역 지정 시 그 역 후보 목록 조회 | 노선 A 승강장→노선 B 승강장 연결, 대체 환승 포함 전체 여정은 미계산 |
| 경유역만 고장 | 경로 위 경유역 경고 전달 | 정차만 하는 역의 설비 고장을 모든 승차자의 통과 불가로 해석 |
| 순환선 | 사용자 제공 다음역으로 방면 정보를 보관 | 최단 경로의 순서를 실제 내·외선으로 간주하거나 전체 원을 돌아가는 선택 추천 |
| 분기/급행/종착 열차 | 노선+다음역이 있어도 정차 패턴/운행 구간 미검증 명시 | 같은 노선이면 모든 후보에 서거나 동일 열차로 이어진다고 판단 |
| 복수 노선 환승역 후보 | `same_line`이 대상 역과의 노선 일부 공유임을 유지 | 현재 이용 노선에서 바로 하차 가능하다는 주장 |
| 입력 역명 누락·모호 | 해당 슬롯 재질문. 최근 조회역/이전 계획 목적지를 현재역으로 보충하지 않음 | “거기”, 역명 2개 순서만으로 현재/목적/고장/다음역 배정 |
| 다음역=현재역, 소속 노선 모순 | 다음역 재입력 요구 | 모순된 값을 가지고 분석 진행 |
| 고장역≠목적지 | **고장역**으로 검색, 목적지 별도 표시 | 목적지 고장이라고 바꿔서 조회 |
| 상태 UNKNOWN/STALE, TTL 경과 | 기존 도구의 상태/신선도 한계 유지, 정상 취급 안 함 | 미확인 설비를 정상으로 채우거나 후보 없음을 접근성 보장으로 해석 |
| 후보 없음/간선 없음 | 후보를 확인하지 못했다고 안내 | 옆 역을 임의로 만들거나 경로가 안전하다고 결론 |
| BE 연결 실패 | 오케스트레이터의 `data_unavailable` 경로로 반환, Mock/이전 값 대입 안 함 | 서울 API나 운영 DB에 새 수집을 자동 실행, 오류를 후보 없음으로 감추기 |
| LLM 미설정/장애 | 같은 슬롯 수집과 코드 기반 분석 사용 | 자유 생성 모델이 없어서 안전 경계가 사라지는 동작 |
| 세션 만료/새 분석 | 수집 정보 소멸/분석 후 재확인 | 지난 대화의 현재역·승차상태를 실시간 상태로 재사용 |

## 예시 대화

다음은 입력 형식과 안전한 설명 수준을 보여주기 위한 예시다. 역 사이의 실제 이동 가능성을 주장하지 않는다.

> 사용자: 열차 안인데 목적지 엘리베이터가 고장났대요.
>
> 챗봇: 현재 역, 현재 노선, 목적지 역, 고장 역, 진행 방면의 다음 정차역을 알려주세요. 열차 안이라면 가장 최근 정차역을 현재 역으로 알려주세요.
>
> 사용자: 현재 강남역, 2호선, 다음 정차역 역삼역.
>
> 챗봇: 목적지 역과 고장 역을 알려주세요.
>
> 사용자: 목적지 사당역, 고장 역 사당역.
>
> 챗봇: 알려주신 이동 정보를 정리하고 사당역의 데이터 소스에서 확인한 후보만 표시합니다. 후보가 실제 앞/뒤인지와 접근 동선은 확인되지 않았습니다. 앞쪽이라면 같은 열차 정차/하차·출구 접근을, 뒤쪽이라면 계단 없는 반대편 이동·재탑승을 먼저 확인해야 합니다. 바로 내리거나 반대편으로 갈아타라는 지시는 하지 않습니다.

표현 지원은 의도적으로 보수적이다. “잠실 가는 중, 아까 거기” 같은 자유로운 답에서 위치와 다음역을 추측하지 않는다. 필드 예시대로 답하면 다중 턴 수집이 완성된다. LLM 슬롯 추출은 향후에도 입력 출처/확신/재확인과 함께 연결해야 한다.

## 향후 BE 계약에 필요한 정보

1. **현재 여정 식별:** 승차 여부, 현재 또는 마지막 정차역, 현재 노선·방향 식별자, 다음 정차역, 서비스일·현재 시각, 가능하면 열차 ID/정차 패턴. 사용자 신고값과 관측값의 출처를 구분한다.
2. **방향 있는 노선 그래프:** `station_line_id`, 방향별 연속 정차역, 분기·순환·급행·종착·운행중단 정보. `ahead/behind`는 이 여정 그래프에서 판정하고 판정 불가도 표현해야 한다.
3. **역 내부 접근성 그래프:** 승강장·대합실·출입구 노드, 연결 설비 ID, 방향 변경/환승/개찰구 경유 가능 여부, 계단 없는 연결 검증, 운영시간·통행 제한. AVAILABLE 설비 수만으로 대체할 수 없다.
4. **외부 이동 동선:** 후보 출구에서 최종 목적지까지의 계단 없는 이동 경로, 경사/횡단/보도 통행 제한, 확인 시각/출처. 좌표 직선 거리만으로 이동 시간을 채우지 않는다.
5. **후보별 근거·불확실성:** 실제 이용 노선과 방향, 현재 열차로 접근 가능 여부, 반대편 이동 필요 여부, 검증된 `path`, 필수 설비와 상태/수집시각/TTL, 미확인 구간과 탈락 사유. 부족하면 `accessible: unknown`을 반환한다.
6. **재계산:** 검증된 대체 경로가 정해진 후에만 우회 시간/환승/출발 시각을 갱신한다. 승차 중 계산은 이미 지불한 집→역·진입·탑승 전 대기를 제외한다.

현재 BE 후보 응답에 위 필드를 AI가 임의 추가하지 않는다. 기존 합성 테스트 fixture를 운영 API나 기본 데이터에 복사하지 않는다. 현장 이동 검증·실열차 연결·음성 입력의 자동 슬롯 추출은 이번 검증 범위 밖이다.

## 검증

변경 전 AI 전체 테스트 324개 통과, 변경 후 335개 통과를 확인했다. 새 회귀 테스트 10개는 `tests/llm/test_directional_alternatives.py`에 있으며, 다중 턴 완성·빈 슬롯 보존·명시적 역 검증·취소·새 주제·TTL·폴백·PARTIAL 표현·소속 노선/동일역 모순·고장역/목적지 분리·서버 오류·수집 시각을 확인한다. 추가 HTTP 회귀 1개(`tests/api/test_chat_api.py`)는 키 없는 TestClient로 같은 세션의 3개 요청을 보내 수집→분석→실제 수집시각과 후보 상세 액션 payload 전달까지 검증한다. 기존 BE 녹화 fixture 시나리오와 도구/오케스트레이터 테스트는 후보 상세 액션과 안전 문장 변경을 반영했다. Mock 기반 기존 폴백 벤치마크 50문항은 50/50 통과했다. 이 기존 벤치마크에는 신규 방면 시나리오가 없으므로 신규 기능 품질 수치로 해석하지 않는다. 외부 LLM 호출, 서울 API 호출, 운영 DB 쓰기 및 실제 휠체어 현장 이동 검증은 수행하지 않았다.
