# 벤치마크 (Evaluation Benchmark)

> 명세 [`AI_DEVELOPMENT_SPEC.md` §8](./AI_DEVELOPMENT_SPEC.md)의 50문항 평가를 실행하는 방법과 결과를 기록한다.
> 결과 숫자는 실제로 돌린 값만 적는다. 실행할 때마다 날짜·엔진·모델과 함께 §4에 추가한다.

---

## 1. 실행

```powershell
python scripts/run_benchmark.py                        # 폴백 엔진 기준선 (키 불필요)
python scripts/run_benchmark.py --engine llm           # LLM 게이트웨이 (AI/.env 키 필요, 모델은 FACTCHAT_MODEL / LLM_PROVIDER)
python scripts/run_benchmark.py --only departure CX04  # 분류나 문항 ID로 골라 실행
python scripts/run_benchmark.py --engine llm --json results.json   # 문항별 결과 저장
python scripts/run_benchmark.py --engine llm --timeout 30         # 타임아웃 영향을 빼고 정확도 측정 (운영 설정은 그대로)
python scripts/run_benchmark.py --engine llm --model gpt-4o-mini  # 다른 모델로 비교
```

- 두 엔진 모두 운영과 같은 `ChatOrchestrator`를 거친다. 폴백 기준선은 "LLM 키 없음"과 같은 경로다.
- LLM 모드에서 호출이 실패한 문항은 폴백으로 답하고, 결과표의 "LLM 응답 / 폴백 응답"에 따로 센다. 폴백 응답이 섞이면 LLM 점수로 보지 않는다.
- 기준 시각은 모든 문항 `12:00` (`cases.json`의 `default_current_time`). 문항마다 새 세션을 쓴다.

## 2. 평가셋 (`src/eval/cases.json`)

| 분류 | 문항 | 예 |
|---|---|---|
| 엘리베이터 상태 (`EL`) | 10 | "강남역 엘리베이터 돼?", "고터 엘리베이터 돼?"(별칭), "2호선에서 엘리베이터 고장 난 역 목록 보여줘" |
| 대체역·우회 (`AL`) | 10 | "사당역 엘리베이터 고장났는데 어디로 가?", "구디 엘리베이터 고장났어? 다른 역 알려줘" |
| 출발 시각 역산 (`DP`) | 15 | "신도림에서 잠실까지 3시 반까지 가려면?", "강남역까지 5시까지 가려면 언제 나와야 해?"(출발역 없음) |
| 문맥 연속 대화 (`CX`) | 10 | ("사당역 엘리베이터 돼?" 다음) "그럼 거기서 잠실까지 4시까지 가려면?" |
| 커버리지 밖 (`CV`) | 5 | "판교역 엘리베이터 상태는?", "부평역 엘리베이터 돼?" |

- 정답은 Mock 데이터(`src/data/mock_data.py`) 기준이다. BE 실데이터로 바꾸면 기대 문장(`text_includes`)을 다시 맞춰야 한다.
- 문항마다 기대값: `card_type`(허용 목록), 필수 도구 `tools`, 하나 이상 필요한 `tools_any`, 불러도 되는 `optional_tools`, 슬롯 `slots`, 문장에 있어야 할 말 `text_includes`, 없어야 할 말 `text_excludes`.
- `resolve_station`은 언제 불러도 감점하지 않는다.

## 3. 채점

| 지표 | 계산 | 명세 목표 |
|---|---|---|
| 도구 선택 정확도 | 필수 도구를 모두 부르고, 허용 목록 밖 도구를 부르지 않은 문항 비율 | 98% 이상 |
| 슬롯 F1 | 도구 인자를 의미 단위 슬롯으로 바꿔 전체 문항 합산(micro) 정밀도·재현율로 계산 | 0.95 이상 |
| 후처리 검증 발동 | LLM 응답 중 `guard_triggered` 수. 검증 전 환각 수에 해당. 결과표에 걸린 표현을 함께 적는다 | 검증 후 환각 0% |
| 응답 시간 | 마지막 문장 `latency_ms`의 P50·P95 | P95 2,000ms (폴백 100ms) |
| card_type 정확도, 문장 검사 | 기대 목록 일치, `text_includes`/`text_excludes` | — |
| 통과율 | 위 모든 항목과 슬롯 완전 일치 | — |

슬롯 정규화 (`slots_from_calls`): 호출 방식이 달라도 같은 의미면 같은 슬롯이 되게 한다.

| 도구 호출 | 슬롯 |
|---|---|
| `get_elevator_status(station_id=X)`, `plan_trip(start_id=X, end_id=X)` | `station:X` |
| `plan_trip(start_id=A, end_id=B, arrive_by=T)` (A≠B) | `origin:A`, `destination:B`, `arrive_by:T` (`depart_at`도 같음) |
| `get_broken_elevators(line_id=L)` | `line:L` |

해석:

- **EL06**: 폴백 엔진은 노선 필터를 읽지 않고 항상 전체 고장 목록을 조회한다. 결과 문장은 맞지만(2호선 고장 역이 Mock상 전부라서) 슬롯이 틀렸다.
- **CX09**: "신촌에서 그 역까지"처럼 새 역과 지칭어가 함께 나오면, 폴백은 지칭어를 무시하고 직전 역(시청)을 출발역으로 넣어 출발·도착이 뒤바뀐다. 사용자에게 반대 방향 경로를 안내하는 오류다.
- 평가셋은 폴백 규칙을 만든 같은 팀이 썼고 말투가 규칙과 비슷하다. **기준선 96%는 낙관적인 값**으로 봐야 한다. 팀원이 쓴 다른 표현(오타, 띄어쓰기 없음, 구어체)을 추가하면 더 정확해진다.
- 폴백 응답 시간은 프로세스 안 계산이라 1ms 미만으로 측정됐다 (P95 0ms).

### 2026-11-13 — LLM 게이트웨이 (FactChat `gpt-5.1`)

같은 50문항을 두 조건으로 돌렸다. 조건마다 1회씩만 실행했고 LLM 응답과 게이트웨이 속도는 실행마다 달라지므로, 몇 문항 차이는 오차 범위로 본다.

- **운영 설정**: 호출 1회 타임아웃 3초 (`config.py` 현재 값). 실제 서비스에서 몇 %가 폴백으로 넘어가는지 본다.
- **측정용 30초** (`--timeout 30`): 타임아웃 영향을 빼고 LLM 자체의 정확도와 응답 시간을 본다. 운영 설정을 바꾼 것은 아니다.

#### 해석

- **정확도는 목표를 넘는다.** 타임아웃 영향을 뺀 최종 측정에서 50문항이 모두 통과했다(도구 선택 100%, 슬롯 F1 1.00). 후처리 검증이 걸린 3건 중 2건(AL09 "권장역", AL10 "우회역")은 가드 오탐이라 일반 표현 목록에 추가했다. 나머지 CV02는 정자역 질문에 강남역을 언급한 실제 근거 없는 표현이다.
- **운영 설정의 실패 3건 중 2건은 폴백 엔진의 알려진 오류다.** 타임아웃으로 폴백된 EL06(노선 필터 무시)과 CX09(출발·도착 뒤바뀜)이다. CX07은 LLM이 대체역 조회를 한 번 더 불러 슬롯이 하나 더 잡힌 것이고, 안내 내용은 맞다.
- **응답 시간이 가장 큰 문제다.** `gpt-5.1`은 호출 1회에 약 1.2~3.3초가 걸린다. 한 질문에 "역 확인 → 조회 → 답변"으로 2~3회 호출하므로 P50이 약 5.5초다. 명세 목표(P95 2초)의 3배 이상이다.
  - 운영 설정(호출당 3초)에서는 **32~44%가 타임아웃으로 폴백**된다(1차 16/50, 최종 22/50). 실행마다 게이트웨이 속도가 달라 차이가 크다.
  - 폴백 응답도 타임아웃까지 기다린 뒤 나가므로 4~6초가 걸린다.
- 결정이 필요한 것(팀): 모델(더 빠른 모델과 비교 측정), 타임아웃을 호출 1회 기준으로 둘지 요청 전체 기준으로 둘지, 명세의 P95 2초 목표를 유지할지.

### 2026-11-13 — 응답 속도 옵션과 모델 비교 (이슈 #17)

LLM 호출 횟수를 줄이는 두 옵션(IMPLEMENTATION_STATUS §4.6)을 넣고 모델별로 다시 쟀다. 모든 측정은 #18 폴백 수정, 범위 밖 역 ID 거부, Gemini `thought_signature` 보존이 들어간 같은 코드다. 조건마다 1회씩만 실행했다.

- **역 사전 확인** (`LLM_PRERESOLVE=true`, `--preresolve`): 문장 속 역을 코드가 먼저 `resolve_station`으로 확인해 프롬프트에 넣는다. 역 확인 왕복 1회가 줄어든다.
- **템플릿 답변** (`LLM_ANSWER_MODE=template`, `--answer-mode template`): 데이터 도구가 성공하면 LLM에 다시 묻지 않고 도구 결과 템플릿으로 문장을 만든다. 답변 문장 왕복 1회가 줄어든다.

#### 해석

- **`gemini-3.5-flash-lite` + 사전 확인 + 템플릿(F) 조합만 명세 목표(P95 2초)를 넘지 않았다.** 운영 타임아웃 3초에서도 50/50 통과, 폴백 0건, 가드 0건, P95 1.5초다. 호출이 대부분 1회로 줄어 타임아웃 위험도 작다.
- **호출 횟수를 줄이는 효과가 모델 교체보다 크다.** 같은 gemini에서 옵션 없음(H) P50 3.1초 → 사전 확인(G) 2.2초 → 사전 확인 + 템플릿(F) 1.0초. `gpt-5.1`도 두 옵션을 켜면 P50 5.5초 → 1.6~1.9초로 줄지만 P95가 3~4초라 목표를 넘고, 3초 타임아웃에서 2건이 폴백된다.
- **템플릿 답변은 정확도에도 유리했다.** LLM이 문장을 쓰는 조건(G, H)에서는 시각을 지어내거나(가드 발동) 필요한 안내를 빠뜨렸다(DP02, DP13). 템플릿은 도구 결과를 그대로 옮기므로 이런 실패가 없다. 대신 문장이 정형화되어 덜 자연스럽다.
- **`gpt-5.1`의 CV05 반복 실패**: 범위 밖 역을 프롬프트에서 금지해도 도구를 부른다. 도구가 오류를 돌려주므로 사용자 안내는 틀리지 않는다.
- 참고로 수정 전 코드로 잰 탐색 측정에서 `gpt-5.4-mini`는 정확도가 76~86%로 낮아(지칭어·범위 밖 처리 실패) 최종 측정에서 뺐다. 이 값은 지금 코드로 다시 재지 않았다.
- 결정이 필요한 것(팀): 모델(`gemini-3.5-flash-lite` 전환 여부), 두 옵션을 기본으로 켤지, 템플릿 문장의 자연스러움을 받아들일지. 지금 기본값은 기존 동작(`gpt-5.1`, 두 옵션 끔)이다.
